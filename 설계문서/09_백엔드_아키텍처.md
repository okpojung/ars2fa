# 09. 백엔드 아키텍처

## 1. 목적

이 문서는 `ars2fa` 백엔드의 애플리케이션 구조, API 모듈, ARS 인증 Gateway, API Key 검증, 인증 로그 저장, 통계/Worker 처리 방식을 정의한다.

백엔드는 아래 요청을 처리한다.

- 사용자 포털 업무 API: `https://ars2fa.baro.me/api/*`
- 관리자 콘솔 업무 API: `https://ars2fa.baro.me/api/admin/*`
- 모바일 앱/SDK 인증 API: `https://ars2fa.baro.me/v1/ars/*`

## 2. 설계 원칙

- 포털 업무 API와 ARS 인증 API Gateway를 논리적으로 분리한다.
- API Key 검증, 앱명/플랫폼 검증, rate limit은 기존 ARS 서버 호출 전에 수행한다.
- API Key 원문과 휴대폰 번호 원문은 저장하지 않는다.
- 인증 요청은 `auth_requests`에 최신 상태를 저장하고, 단계별 이벤트는 `auth_events`에 append-only로 저장한다.
- 관리자 승인, Key 발급/정지/폐기, CSV 다운로드 등 운영 행위는 감사 로그를 남긴다.
- 초기 단계는 단일 Backend 서비스로 시작하되, 확장 단계에서 Worker와 조회/집계 부하를 분리할 수 있게 설계한다.

## 3. 확정 기술 스택

ars2fa 백엔드 스택은 아래로 확정한다.

```text
NestJS + TypeScript + PostgreSQL + Prisma + Redis + BullMQ
```

인증/검증/로그/API 문서까지 포함한 전체 스택은 다음과 같다.

| 영역 | 확정 스택 | 설명 |
|---|---|---|
| Runtime | Node.js 20 LTS 이상 | Coolify, Docker, PM2, Worker 운영이 쉽고 TypeScript 생태계가 풍부하다. |
| Framework | NestJS | 모듈, Controller, Service, Guard, Interceptor 구조가 명확해 신청/승인/API Gateway 기능 분리에 적합하다. |
| Language | TypeScript | DTO, API 응답, DB 모델 타입을 명확히 해 운영성 오류를 줄인다. |
| DB | PostgreSQL | API 신청, API Key, 인증 로그, 감사 로그처럼 정합성이 중요한 데이터를 저장한다. |
| ORM/Query | Prisma | migration, schema 관리, type-safe query, 개발 생산성이 좋다. |
| Cache | Redis | API Key 검증 캐시, rate limit 카운터, 월 사용량 카운터를 빠르게 처리한다. |
| Queue | BullMQ | 승인/반려 알림, CSV 생성, 일별 통계 집계 같은 비동기 작업을 처리한다. |
| Validation | class-validator + class-transformer | NestJS DTO validation pipe와 자연스럽게 통합된다. |
| Logging | Pino | 빠른 구조화 로그, request id, 민감정보 마스킹에 적합하다. |
| Auth | HttpOnly Cookie + JWT Session | 사용자/관리자 웹 로그인에 사용한다. API Key 인증과 웹 로그인 인증을 분리한다. |
| API Docs | Swagger/OpenAPI | 포털 API와 `/v1/ars/*` API 문서를 자동 생성한다. |
| Test | Jest + Supertest | Service 단위 테스트와 HTTP API 통합 테스트를 작성한다. |

### 3.1 NestJS로 확정하는 이유

NestJS는 백엔드 기능을 모듈 단위로 나누기 좋다.

ars2fa는 기능이 아래처럼 명확하게 분리된다.

- 회원/로그인.
- API 신청.
- 관리자 심사.
- API Key 발급/검증.
- ARS 인증 Gateway.
- 인증 로그/통계.
- 알림/Worker.

NestJS는 이런 기능을 각각 Module, Controller, Service, Guard로 나눌 수 있다.

```text
Controller: HTTP 요청을 받는 창구
Service: 실제 업무 로직 처리
Guard: 로그인/권한/API Key 검사
Interceptor: 로그, 응답 포맷, 마스킹 처리
Module: 관련 기능 묶음
```

Fastify도 빠른 프레임워크이지만, ars2fa는 초고성능 단일 API보다 승인/권한/로그/모듈 분리가 더 중요하다. 따라서 구조가 명확한 NestJS를 확정한다.

### 3.2 PostgreSQL + Prisma로 확정하는 이유

ars2fa 데이터는 정합성이 중요하다.

예를 들어:

- 관리자가 신청을 승인하면 API Key가 정확히 발급되어야 한다.
- Key가 정지되면 즉시 인증 API 호출이 막혀야 한다.
- 인증 요청 로그는 나중에 분쟁이나 장애 분석에 사용할 수 있어야 한다.
- 감사 로그는 관리자 작업 이력으로 남아야 한다.

이런 데이터에는 PostgreSQL이 적합하다.

Prisma를 선택하는 이유:

- DB schema를 코드로 관리하기 쉽다.
- migration 이력이 남는다.
- TypeScript 타입이 자동 생성되어 오타와 타입 실수를 줄인다.
- `users`, `api_applications`, `api_keys`, `auth_requests` 같은 관계형 테이블을 다루기 쉽다.

### 3.3 Supabase Self-hosted를 기본 스택에서 제외하는 이유

easymindmap은 Supabase Self-hosted를 사용한다.

그 이유는 easymindmap에 아래 기능이 많기 때문이다.

- Supabase Auth.
- Supabase Realtime.
- Supabase Storage.
- 마인드맵 협업/실시간 상태.
- 공개 HTML/파일 저장.

반면 ars2fa의 핵심은 다음이다.

- API 신청/승인.
- API Key 발급/검증.
- ARS 인증 API 중계.
- 인증 로그/통계.
- 관리자 감사 로그.

ars2fa 초기 단계에는 Supabase Realtime이나 Storage의 필요성이 낮다. Supabase Self-hosted를 도입하면 기능은 많지만 운영 구성도 함께 커진다.

따라서 ars2fa는 초기 확정 스택을 다음처럼 단순화한다.

```text
PostgreSQL 직접 운영 + Prisma migration + NestJS Auth/Guard 구현
```

향후 아래 요구가 생기면 Supabase 도입을 다시 검토할 수 있다.

- 파일/문서 저장소가 필요하다.
- 실시간 dashboard push가 필요하다.
- 별도 Auth 관리 UI가 필요하다.
- 내부 운영자가 Supabase Studio를 적극 사용해야 한다.

### 3.4 Redis + BullMQ로 확정하는 이유

Redis는 빠른 임시 저장소로 사용한다.

ars2fa에서 Redis가 필요한 이유:

- API Key 검증 결과를 몇 분간 캐시해 DB 조회를 줄인다.
- API Key별 분당 호출 제한을 빠르게 계산한다.
- 월 호출량 카운터를 관리한다.
- 관리자 통계/CSV 생성 작업을 queue로 넘긴다.

BullMQ는 Redis 기반 작업 큐이다.

예를 들어 CSV 다운로드는 즉시 끝나지 않을 수 있다. 이런 작업을 API 요청 안에서 오래 처리하면 사용자가 기다려야 한다. BullMQ에 작업을 넣고 Worker가 뒤에서 처리하면 API 서버가 가벼워진다.

```text
사용자 CSV 다운로드 요청
  -> Backend가 BullMQ queue에 작업 등록
  -> Worker가 DB에서 로그 조회
  -> CSV 파일 생성
  -> 완료 상태 저장
  -> 사용자가 다운로드
```

```mermaid

        API->>DB: key_hash, application_app 조회
```

## 9. API Key 검증 구조

### 9.1 검증 순서

1. `api_key` 존재 여부 확인.
2. API Key 원문을 HMAC/SHA 방식으로 해시.
3. `api_keys.key_hash` 조회.
4. Key 상태가 `ACTIVE`인지 확인.
5. 연결된 `api_applications` 상태가 `APPROVED`인지 확인.
6. `mobile_app_name`, `client_platform`, `package_name`/`bundle_id`가 승인된 `application_apps`와 일치하는지 확인.
7. 허용 IP가 설정된 경우 `X-Forwarded-For` 기준으로 확인.
8. API Key별 rate limit/monthly limit 확인.

### 9.2 Redis Cache

| Key | TTL | 내용 |
|---|---:|---|
| `api-key:{keyHash}` | 5분 | Key ID, application ID, 상태, 한도 |
| `api-key-apps:{apiKeyId}` | 5분 | 승인 앱명/플랫폼/package/bundle 목록 |
| `rate:{apiKeyId}:{minute}` | 1~2분 | 분당 호출 카운터 |
| `monthly:{apiKeyId}:{yyyyMM}` | 월말까지 | 월 호출 카운터 |

Key 상태 변경, 정지, 폐기, 한도 변경 시 관련 cache를 즉시 삭제한다.

## 10. 인증 로그 저장 정책

### 10.1 `auth_requests`

최신 상태를 저장한다.

| 단계 | 처리 |
|---|---|
| install 요청 전 | Key 검증 실패는 `auth_events`에만 남길 수 있음 |
| install 요청 접수 | `INSTALL_REQUESTED` 생성 |
| install 성공 | `INSTALL_SUCCEEDED`, `appuuid`, provider 응답 저장 |
| confirm 성공 | `AUTH_SUCCEEDED`, `app_cid` 마스킹/해시 저장 |
| confirm 수동 필요 | `MANUAL_REQUIRED` |
| recheck 성공 | `MANUAL_SUCCEEDED` |
| 실패 | `INSTALL_FAILED`, `AUTH_FAILED`, `MANUAL_FAILED` |

### 10.2 `auth_events`

모든 요청/응답 단계는 append-only 이벤트로 저장한다.

- `event_type`: `INSTALL`, `CONFIRM`, `RECHECK`, `STATUS_QUERY`, `ERROR`.
- `endpoint`: `/v1/ars/install` 등.
- request/response payload는 마스킹 후 JSON으로 저장.
- provider 오류는 `ARS_PROVIDER_ERROR`로 표준화하고 원본 메시지는 민감정보 제거 후 저장.

## 11. 휴대폰 번호/민감정보 처리

```text
normalized_phone = 숫자만 추출한 전화번호
phone_hash = HMAC_SHA256(PHONE_HASH_SECRET, normalized_phone)
phone_masked = 010****1234
```

로그 마스킹 대상:

| 필드 | 처리 |
|---|---|
| `api_key` | 저장 금지, prefix만 로그 |
| `Authorization` | 저장 금지 |
| `appphone` | hash/masked 변환 |
| `app_cid` | hash/masked 변환 |
| `inst_phone_no` | masked |
| `prnts_phone_no` | masked |

## 12. 관리자 승인 및 Key 발급 흐름

```mermaid
sequenceDiagram
    participant Admin
    participant API as Backend
    participant DB
    participant Notify as Notification

    Admin->>API: POST /api/admin/applications/:id/approve
    API->>DB: 신청/앱 정보 잠금 조회
    API->>API: 승인 가능 상태 검증
    API->>API: raw API Key 생성
    API->>API: key_hash, key_prefix 생성

```

Key 원문은 응답 직후 다시 조회할 수 없다. 사용자가 분실한 경우 재발급한다.

## 13. 트랜잭션 경계

| 업무 | 트랜잭션 |
|---|---|
| API 신청 제출 | 신청 상태 변경 + 이력 저장 |
| 보완 요청 | 신청 상태 변경 + review_history + audit_log |
| 승인/Key 발급 | 신청 승인 + 앱 승인 + Key 저장 + review_history + audit_log |
| Key 정지/폐기 | Key 상태 변경 + cache invalidation event + audit_log |
| install 성공 | auth_requests 생성/업데이트 + auth_events append |
| confirm 성공 | auth_requests 업데이트 + phone hash 저장 + auth_events append |

외부 알림 발송은 DB 트랜잭션 안에서 직접 보내지 않고 queue에 등록한다.

## 14. Worker 아키텍처

초기 단계에서는 Backend 프로세스 안에서 간단한 작업을 처리할 수 있으나, 확장 단계부터 Worker를 분리한다.

```text
Worker queues
  ├── notification.approval
  ├── notification.limit-warning
  ├── statistics.daily-rollup
  ├── export.auth-requests-csv
  ├── audit.retention
  └── provider.healthcheck
```

| Queue | 설명 |
|---|---|
| `notification.approval` | 승인/반려/보완 요청 알림 |
| `notification.limit-warning` | 월 한도 80%/100% 알림 |
| `statistics.daily-rollup` | 일별 인증 통계 집계 |
| `export.auth-requests-csv` | 인증 로그 CSV 생성 |
| `audit.retention` | 보관 기간 만료 로그 정리/익명화 |
| `provider.healthcheck` | 기존 ARS 서버 synthetic check |

## 15. 오류 처리

공통 오류 응답:

```json
{
  "return": false,
  "error_code": "APP_NOT_ALLOWED",
  "message": "승인되지 않은 모바일 앱입니다.",
  "request_id": "req_01HX..."
}
```

| HTTP | 코드 | 처리 |
|---|---|---|
| 400 | `MISSING_REQUIRED_PARAMETER` | DTO 필수값 누락 |
| 401 | `UNAUTHORIZED_API_KEY` | Key 없음/해시 불일치 |
| 403 | `API_KEY_DISABLED` | 정지/폐기 Key |
| 403 | `APP_NOT_ALLOWED` | 앱명/플랫폼 불일치 |
| 404 | `AUTH_SESSION_NOT_FOUND` | confirm/recheck 대상 없음 |
| 409 | `AUTH_SESSION_EXPIRED` | 인증 세션 만료 |
| 429 | `RATE_LIMIT_EXCEEDED` | 호출 한도 초과 |
| 502 | `ARS_PROVIDER_ERROR` | 기존 ARS 서버 장애 |

## 16. 관측성

### 16.1 로그 필드

|---|---|

| `mobile_app_name` | 요청 앱명 |

| `status_code` | HTTP 응답 |
| `duration_ms` | 처리 시간 |
| `provider_duration_ms` | 기존 ARS 서버 호출 시간 |
| `error_code` | 표준 오류 코드 |

### 16.2 Metrics

- `/v1/ars/install` 요청 수.
- `/v1/ars/confirm` 요청 수.
- provider timeout/5xx 수.
- 인증 성공률.
- 수동 인증 전환율.
- API Key 검증 실패 수.
- Redis rate limit hit 수.
- DB query duration.
- Worker queue depth.

## 19. 테스트 전략

|---|---|

## 20. 확장/분리 기준

아래 조건이 발생하면 백엔드를 기능별로 분리한다.

| 조건 | 분리 방향 |
|---|---|
| 인증 API 호출이 포털 API에 영향을 줌 | `ars-gateway` 서비스를 별도 배포 |
| 통계/CSV 작업이 API 응답을 지연 | Worker pool 분리/증설 |
| 인증 로그 조회가 DB 부하 유발 | read replica 또는 검색 전용 저장소 도입 |
| 관리자 보안 정책 강화 | admin API를 VPN/internal route로 분리 |
| 앱 500개 이상 운영 | NPM/L4, App VM 다중화, DB replica 검토 |
