# 01. 개념 및 범위

## 1. 목적

`ars2fa`는 발신 ARS 방식의 휴대폰 인증 API를 외부 서비스가 신청, 승인, 발급, 조회할 수 있게 하는 API 신청/운영 사이트이다.

서비스 제공자는 ARS 인증 API 사용 권한을 API Key 단위로 통제하고, 사용자는 승인된 API Key를 `ars_auth` Flutter 위젯 또는 자체 클라이언트에 설정해 모바일 앱에서 ARS 인증을 수행한다.

## 2. 배경

현재 `ars_auth` 저장소의 Flutter 위젯은 다음 서버 API를 직접 호출한다.

| 단계 | Android URL | iOS URL | 주요 파라미터 |
|---|---|---|---|
| 인증 설치 요청 | `install_app.php` | `install_app_ios.php` | `appsid`, `app_os_type`, `app_os_version`, `app_cp_carr`, `gcmid`, `playerid` |
| 인증 확인 요청 | `confirm_auth.php` | `confirm_auth_ios.php` | `appuuid`, `appsid`, `applng`, `applat` |
| 수동 인증 확인 | `confirm_auth_recheck.php` | `confirm_auth_recheck.php` | `appphone`, `appuuid` |

이 구조는 인증 실행 자체에는 충분하지만, API 사용 고객/앱별 구분과 과금, 차단, 현황 조회를 위해 아래 식별자가 추가로 필요하다.

- `api_key`: 승인된 API 사용자를 식별하는 키.
- `mobile_app_name`: API를 사용하는 모바일 앱 명칭.
- 필요 시 `package_name`, `bundle_id`, `platform`: 모바일 앱 실체 검증 및 운영 통계 분리용.

## 3. 서비스 대상

| 구분 | 설명 |
|---|---|
| API 사용자 | ARS 인증 API를 사용할 사업자/개발자. 회원 가입 후 API 사용 신청을 등록한다. |
| 관리자 | 신청 심사, 승인/반려, API Key 발급/폐기, 사용량/오류 모니터링을 담당한다. |
| 최종 사용자 | API 사용자의 모바일 앱에서 발신 ARS 인증을 수행하는 휴대폰 소유자. |
| ARS 인증 서버 | 기존 `barocall.baro.so` 계열의 ARS 설치/확인 API 또는 ars2fa가 래핑하는 백엔드 API. |

## 4. 공식 URL

| 구분 | URL | 설명 |
|---|---|---|
| 사용자 포털 | `https://ars2fa.baro.me` | 회원 가입, API 신청, API Key 관리, 인증 현황 조회 |
| 관리자 콘솔 | `https://ars2fa.baro.me/admin` | 신청 심사, 승인/반려, API Key 운영, 전체 인증 로그 모니터링 |
| 인증 API | `https://ars2fa.baro.me/v1/ars/*` | `ars_auth` 위젯과 외부 클라이언트가 호출하는 ARS 인증 API |
| 포털 API | `https://ars2fa.baro.me/api/*` | 사용자 포털/관리자 콘솔에서 사용하는 업무 API |

관리자 콘솔은 별도 서브도메인이 아니라 같은 도메인의 `/admin` 경로를 사용한다. 따라서 프록시, 라우팅, 세션 쿠키, CORS 정책은 동일 사이트 기준으로 설계한다.

## 5. 핵심 가치

1. **API 사용 주체 식별**
   - 동일 ARS 인증 API를 여러 앱이 사용할 때 `api_key`와 `mobile_app_name`으로 호출 주체를 명확히 구분한다.
2. **승인 기반 접근 제어**
   - 회원 가입만으로는 API를 사용할 수 없고, 관리자가 신청을 승인해야 API Key가 활성화된다.
3. **운영 현황 조회**
   - API 사용자는 본인의 API Key별 인증 요청 수, 성공/실패 수, 최근 인증 상태를 조회한다.
4. **감사 가능성**
   - 신청, 승인, API Key 발급/폐기, 인증 요청 로그를 DB에 남겨 장애 대응과 부정 사용 추적에 활용한다.

## 6. 범위

### 포함

- 회원 가입/로그인/계정 관리.
- API 사용 신청 등록.
- 관리자 신청 심사 및 승인/반려.
- API Key 발급, 재발급, 비활성화.
- `ars_auth`용 API 호출 파라미터 개정안 작성.
- API Key별 인증 현황 조회.
- DB 테이블 설계.
- 운영/보안 고려사항.

### 제외

- ARS 통신사 인프라 자체 구축.
- 실제 과금 정산 시스템의 상세 구현.
- 모바일 스토어 심사, 배포 자동화.
- 기존 `ars_auth`, `BS_Point` 저장소의 코드 변경.

## 7. 참조 앱 연동 개념

`BS_Point`는 `ars_auth` 패키지의 `LoginARS` 위젯을 사용하고, 인증 완료 시 콜백으로 받은 `userInfo`를 저장한다.

```dart
LoginARS(
  useOnlyCallPermission: true,
  onAuthComplete: (userInfo) async {
    await ref
        .read(authProvider.notifier)
        .login(userInfo['app_cid'] ?? '', userInfo);
  },
)
```

개정 후에는 `LoginARS` 또는 하위 `NetworkRepository`가 API 호출 시 `api_key`와 `mobile_app_name`을 함께 전달하도록 확장한다.

```dart
LoginARS(
  apiKey: '발급받은_API_KEY',
  mobileAppName: 'BS Point',
  useOnlyCallPermission: true,
  onAuthComplete: (userInfo) {
    // 기존과 동일하게 인증 결과 저장
  },
)
```

## 8. 주요 정책

- API Key는 승인된 API 신청 건에만 발급한다.
- 하나의 회원은 여러 API 신청을 보유할 수 있다.
- 하나의 API 신청은 운영 정책에 따라 여러 앱(Android/iOS) 정보를 가질 수 있다.
- API Key는 서버에는 해시값으로 저장하고, 원문은 발급 시 한 번만 노출한다.
- ARS 인증 요청 로그는 개인정보 보호를 위해 전화번호 원문 대신 마스킹값과 해시값을 분리 저장한다.
