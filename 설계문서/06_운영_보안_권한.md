# 06. 운영, 보안, 권한 설계

## 1. 권한 모델

### 1.1 사용자 권한

| 권한 | 설명 |
|---|---|
| `USER_OWNER` | 회사/서비스 대표 계정. API 신청, Key 확인, 현황 조회 가능 |
| `USER_DEVELOPER` | API Key 조회, 기술 설정, 인증 현황 조회 가능 |
| `USER_VIEWER` | 인증 현황과 통계 조회만 가능 |

### 1.2 관리자 권한

| 권한 | 설명 |
|---|---|
| `SUPER_ADMIN` | 모든 관리자 기능 접근 |
| `REVIEWER` | API 신청 심사, 승인/반려, 보완 요청 |
| `OPERATOR` | 인증 로그, 장애 로그, 사용량 조회 |
| `KEY_MANAGER` | API Key 발급, 정지, 폐기, 한도 변경 |

관리자 권한은 최소 권한 원칙을 적용하고, 승인/Key 폐기 같은 고위험 작업은 감사 로그를 필수 저장한다.

## 2. API Key 보안

### 2.1 저장

- 원문 API Key는 발급 시 한 번만 노출한다.
- DB에는 `key_hash`, `key_prefix`만 저장한다.
- `key_hash`는 서버 비밀값을 사용하는 HMAC 방식을 권장한다.

```text
key_hash = HMAC_SHA256(server_secret, raw_api_key)
```

### 2.2 전송

- 모든 API는 HTTPS만 허용한다.
- 모바일 앱은 `api_key`를 요청 본문 또는 `Authorization` 헤더로 전송한다.
- 로그에는 API Key 원문을 저장하지 않고 prefix만 남긴다.

### 2.3 재발급/폐기

| 작업 | 처리 |
|---|---|
| 재발급 | 새 Key 발급 후 기존 Key는 유예 기간을 두거나 즉시 `ROTATED` 처리 |
| 정지 | `SUSPENDED` 상태로 변경, 호출 즉시 차단 |
| 폐기 | `REVOKED` 상태로 변경, 복구 불가 |
| 만료 | `EXPIRED` 상태로 자동 변경 |

## 3. 인증 API 보안 검증

API Gateway는 ARS 인증 서버 호출 전에 다음 순서로 검증한다.

1. 필수 파라미터 존재 여부.
2. API Key 해시 조회 및 상태 확인.
3. API Key가 연결된 신청 건이 승인 상태인지 확인.
4. `mobile_app_name`이 승인된 앱 목록에 있는지 확인.
5. `client_platform`과 `package_name`/`bundle_id`가 승인 정보와 맞는지 확인.
6. 허용 IP 정책이 설정된 경우 호출 IP 확인.
7. 분당/월간 호출 한도 확인.
8. 이상 호출 패턴 탐지.

검증 실패 시 기존 ARS 서버를 호출하지 않고 표준 오류 응답을 반환한다.

## 4. 개인정보 보호

| 항목 | 정책 |
|---|---|
| 휴대폰 번호 | 원문 저장 금지. 마스킹값과 HMAC 해시만 저장 |
| 요청 로그 | `api_key`, `appphone`, `app_cid`는 마스킹 |
| 화면 조회 | 전화번호는 `010****1234` 형식으로 표시 |
| CSV 다운로드 | 다운로드 권한 제한, 다운로드 감사 로그 저장 |
| 관리자 조회 | 상세 로그 접근 권한 분리 |

## 5. 모니터링

### 5.1 지표

| 지표 | 설명 |
|---|---|
| install 요청 수 | API Key/앱/플랫폼별 설치 요청 |
| confirm 요청 수 | 인증 확인 요청 |
| 인증 성공률 | `AUTH_SUCCEEDED / 전체 confirm` |
| 수동 인증 전환율 | `MANUAL_REQUIRED / 전체 confirm` |
| 재시도율 | `RETRY_REQUIRED / 전체 confirm` |
| ARS 서버 오류율 | 기존 ARS 서버 5xx 또는 timeout |
| Key 검증 실패 수 | 미승인/정지/앱명 불일치 호출 |
| 응답 시간 | Gateway 및 기존 ARS 서버 호출 latency |

### 5.2 알림 조건

| 조건 | 알림 대상 |
|---|---|
| ARS 서버 오류율 급증 | 운영자 |
| 특정 API Key 실패율 급증 | 운영자, API 사용자 |
| 정지 Key 반복 호출 | 운영자 |
| 월 호출 한도 80% 초과 | API 사용자 |
| 월 호출 한도 초과 | API 사용자, 운영자 |
| 관리자 고위험 작업 | 보안 담당자 또는 SUPER_ADMIN |

## 6. 감사 로그

아래 행위는 반드시 감사 로그에 남긴다.

- 관리자 로그인/실패.
- API 신청 승인, 반려, 보완 요청.
- API Key 발급, 재발급, 정지, 폐기.
- 호출 한도 변경.
- 사용자 또는 관리자 권한 변경.
- 인증 로그 CSV 다운로드.
- 개인정보성 데이터 조회.

감사 로그 필수 항목:

| 항목 | 설명 |
|---|---|
| 행위자 | 사용자/관리자/시스템 |
| 행위 | 예: `API_KEY_SUSPEND` |
| 대상 | 신청 ID, Key ID, 사용자 ID 등 |
| 요청 IP | 접속 IP |
| User-Agent | 브라우저/클라이언트 |
| 변경 전/후 | 상태 변경 시 JSON 형태 |
| 시각 | 서버 기준 timestamp |

## 7. 장애 대응

### 7.1 기존 ARS 서버 장애

1. Gateway timeout 또는 5xx 증가 감지.
2. 신규 install 요청은 `ARS_PROVIDER_ERROR`로 실패 처리.
3. 장애 기간과 영향 API Key를 집계.
4. 사용자 포털 공지 또는 알림 발송.
5. 장애 종료 후 실패 로그 재분석.

### 7.2 API Key 오남용

1. 특정 Key의 호출량 급증 감지.
2. 임계치 초과 시 자동 rate limit 적용.
3. 운영자 확인 후 `SUSPENDED` 처리 가능.
4. 사용자에게 재발급 안내.
5. 감사 로그와 인증 로그 보존.

### 7.3 개인정보 노출 의심

1. 의심 요청/다운로드 감사 로그 확인.
2. 관련 계정 임시 잠금.
3. API Key 정지 또는 재발급.
4. 영향 범위 산정.
5. 내부 보안 정책에 따른 후속 조치.

## 8. 배포 환경

| 환경 | 용도 |
|---|---|
| Local | 개발자 로컬 개발 |
| Test | API 사용자 테스트 Key 검증 |
| Staging | 운영 배포 전 검증 |
| Production | 실제 운영 |

### 8.1 운영 도메인

| 구분 | URL | 라우팅 대상 |
|---|---|---|
| 사용자 포털 | `https://ars2fa.baro.me` | Frontend SPA |
| 관리자 콘솔 | `https://ars2fa.baro.me/admin` | Frontend SPA의 관리자 라우트 또는 Admin SPA |
| 포털/관리자 업무 API | `https://ars2fa.baro.me/api/*` | Backend API |
| ARS 인증 API | `https://ars2fa.baro.me/v1/ars/*` | Backend API Gateway |

관리자 콘솔은 `/admin` 경로를 사용하므로 관리자 인증/권한 검사는 프론트엔드 라우팅이 아니라 백엔드 API에서 반드시 수행한다. Nginx Proxy Manager 또는 애플리케이션 라우터는 `/admin` 새로고침 요청을 SPA 엔트리로 전달해야 한다.

환경별 API Key prefix:

| 환경 | Prefix |
|---|---|
| Test | `ars2fa_test_` |
| Production | `ars2fa_live_` |

## 9. Rate Limit 정책

기본 정책 예시:

| 기준 | 제한 |
|---|---|
| API Key 분당 요청 | 60회 |
| API Key 월 요청 | 신청 승인 시 설정 |
| 동일 `appsid` confirm 반복 | 5회 |
| 동일 전화번호 해시 반복 실패 | 일정 횟수 초과 시 지연 또는 차단 |

정책 초과 시 응답:

```json
{
  "return": false,
  "error_code": "RATE_LIMIT_EXCEEDED",
  "message": "API 호출 한도를 초과했습니다.",
  "retry_after_seconds": 60
}
```

## 10. 포털 화면 보안

- 로그인은 HTTPS에서만 허용.
- 비밀번호는 강한 해시 알고리즘으로 저장.
- 관리자 콘솔은 MFA 적용을 권장.
- CSRF 방어와 SameSite 쿠키 정책 적용.
- 세션 idle timeout 적용.
- CSV 다운로드와 Key 조회 화면은 재인증 또는 추가 확인 적용.
- XSS 방지를 위해 사용자 입력값은 출력 시 escape 처리.

## 11. 모바일 앱 보안 고려사항

- API Key는 앱 바이너리에 포함될 수 있으므로 유출 가능성을 전제로 운영한다.
- 가능하면 원격 설정 또는 서버 중계 방식으로 Key를 관리한다.
- 패키지명/Bundle ID, 앱 서명 인증서 fingerprint 등 추가 검증을 단계적으로 도입한다.
- 디버그 로그에는 API Key와 전화번호가 출력되지 않도록 한다.
- `BS_Point`처럼 `Constants.isDebugMode`가 켜진 앱은 운영 배포 전 인증 로그 출력을 비활성화한다.
