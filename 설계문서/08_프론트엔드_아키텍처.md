# 08. 프론트엔드 아키텍처

## 1. 목적

이 문서는 `ars2fa` 사용자 포털과 관리자 콘솔의 프론트엔드 구조를 정의한다.

프론트엔드는 단일 도메인 `https://ars2fa.baro.me`에서 동작하며, 사용자 포털은 루트 경로(`/`), 관리자 콘솔은 `/admin` 경로를 사용한다.

## 2. 설계 원칙

- 사용자 포털과 관리자 콘솔은 같은 배포 단위로 시작하되, 라우팅/권한/메뉴/상태를 명확히 분리한다.
- 관리자 권한 검사는 프론트엔드 가드에 의존하지 않고 백엔드 API에서 반드시 재검증한다.
- API Key 원문은 발급 직후 1회만 화면에 표시하고, 이후에는 prefix와 Key ID만 표시한다.
- 휴대폰 번호와 API Key는 화면, console log, error tracking payload에서 마스킹한다.
- 초기 단계(Coolify 단일 서버)에서 단순하게 배포하고, 확장 단계에서 사용자 포털/Admin SPA 분리 배포가 가능하도록 디렉터리와 라우팅을 설계한다.

## 3. 확정 기술 스택

ars2fa 프론트엔드 스택은 아래로 확정한다.

```text
React + TypeScript + Vite + React Router + TanStack Query + Zustand
```

폼/검증/UI/차트/테스트까지 포함한 전체 스택은 다음과 같다.

| 영역 | 확정 스택 | 설명 |
|---|---|---|
| Framework | React | 사용자 포털과 관리자 콘솔을 컴포넌트 단위로 구성한다. |
| Language | TypeScript | API 응답, 화면 상태, 폼 데이터 타입을 명확히 해 실수를 줄인다. |
| Build Tool | Vite | 개발 서버가 빠르고, Coolify에서 정적 SPA 빌드/배포가 단순하다. |
| Routing | React Router | `/`, `/admin`, `/applications`, `/auth-requests` 같은 path 기반 화면 전환을 담당한다. |
| Server State | TanStack Query | API 목록/상세/통계 조회, 캐시, 로딩/오류 상태, 데이터 갱신을 관리한다. |
| Client State | Zustand | 사이드바 상태, 테마, wizard 임시 상태 등 브라우저 안의 UI 상태를 가볍게 관리한다. |
| Form | React Hook Form | API 신청, 관리자 심사, Key 한도 변경 같은 입력 화면을 효율적으로 만든다. |
| Validation | Zod | 프론트엔드 폼 검증 스키마를 TypeScript 타입과 함께 관리한다. |
| UI Component | Ant Design | 관리자 테이블, 필터, 폼, DatePicker, Modal 등 업무 화면 생산성이 높다. |
| Chart | Recharts | 인증 요청 수, 성공률, 실패율, 월별 사용량 차트를 구현한다. |
| API Client | Axios | 인증 오류, request id, 공통 error handling, 응답 마스킹 interceptor를 적용한다. |
| Test | Vitest + Testing Library | 폼 검증, 권한 guard, 목록 필터 같은 화면 단위 테스트를 작성한다. |

### 3.1 Next.js를 초기 스택에서 제외하는 이유

초기 ars2fa는 Next.js가 아니라 React + Vite SPA로 구현한다.

이유는 다음과 같다.

1. ars2fa의 핵심 화면은 로그인 후 사용하는 사용자 포털과 관리자 콘솔이다.
2. 검색엔진에 잘 노출되어야 하는 공개 콘텐츠가 많지 않다.
3. `/admin`과 인증 현황 화면은 SEO보다 보안, 권한, API 조회가 더 중요하다.
4. Vite SPA는 Coolify에서 빌드/배포가 단순하고 운영 구조가 가볍다.
5. SSR 서버를 별도로 운영하지 않아도 되므로 초기 인프라가 단순하다.

### 3.2 SSR이란?

SSR은 Server-Side Rendering의 약자이며, 한국어로는 "서버 사이드 렌더링"이라고 한다.

일반적인 React SPA는 브라우저가 빈 HTML을 받은 뒤 JavaScript를 실행해서 화면을 만든다.

```text
SPA 방식
브라우저가 HTML 받음
  -> JavaScript 다운로드
  -> 브라우저가 화면을 그림
```

SSR은 서버가 미리 HTML 화면을 만들어서 브라우저에 보내준다.

```text
SSR 방식
서버가 HTML 화면을 미리 만듦
  -> 브라우저가 완성된 HTML을 받음
  -> JavaScript가 붙어서 동작 가능해짐
```

SSR의 장점:

- 검색엔진이 페이지 내용을 더 잘 읽을 수 있다.
- 공개 페이지의 첫 화면 표시가 빨라질 수 있다.
- 블로그, 뉴스, 상품 상세, 마케팅 페이지처럼 외부 검색 유입이 중요한 서비스에 유리하다.

SSR의 단점:

- 서버 렌더링을 위한 Node 서버 운영이 필요하다.
- 캐시, 세션, 배포 구조가 SPA보다 복잡해질 수 있다.
- 관리자/로그인 기반 업무 시스템에서는 장점이 크지 않을 수 있다.

ars2fa 판단:

| 항목 | 판단 |
|---|---|
| 사용자 포털 | 로그인 후 사용하는 업무 화면 중심이므로 SSR 필요 낮음 |
| 관리자 콘솔 `/admin` | 검색 노출 대상이 아니므로 SSR 불필요 |
| 인증 현황/통계 | 로그인 후 API 조회 화면이므로 SSR 불필요 |
| 공개 마케팅 페이지 | 향후 생기면 SSR 검토 가능 |

따라서 초기 구현은 React + Vite SPA로 확정한다. 나중에 공개 마케팅 페이지가 중요해지면 전체 포털을 Next.js로 바꾸기보다 `www` 또는 별도 marketing 앱만 Next.js로 분리하는 방식을 우선 검토한다.

## 9. 상태 관리

### 9.1 서버 상태

TanStack Query의 query key를 업무 도메인별로 분리한다.

```text
auth.currentUser
applications.list(filters)
applications.detail(applicationId)
apiKeys.list(applicationId)
apiKeys.detail(apiKeyId)
authRequests.list(filters)
statistics.summary(filters)
admin.applications.pending(filters)
admin.auditLogs.list(filters)
```

상태 변경 후에는 관련 query를 무효화한다.

| Mutation | Invalidate |
|---|---|
| API 신청 제출 | `applications.list`, `applications.detail` |
| 보완 후 재제출 | `applications.detail`, `admin.applications.pending` |
| 관리자 승인/반려 | `applications.detail`, `admin.applications.pending`, `apiKeys.list` |
| Key 재발급 | `apiKeys.list`, `apiKeys.detail` |
| Key 정지/폐기 | `apiKeys.list`, `apiKeys.detail`, `statistics.summary` |

### 9.2 클라이언트 상태

| 상태 | 저장 위치 |
|---|---|
| 로그인 사용자 요약 | Query cache |
| access token | HttpOnly cookie 권장. 불가 시 memory 우선 |
| sidebar 접힘/테마 | localStorage 가능 |
| API 신청 wizard 임시 상태 | form state 또는 sessionStorage |
| 관리자 필터 조건 | URL query string |

## 10. API Client 설계

### 10.1 요청 공통 처리

- `credentials: 'include'` 또는 Authorization token 정책을 일관되게 적용한다.
- 모든 요청에 `X-Request-Id`를 생성해 전달한다.
- `401`은 로그인 만료 처리, `403`은 권한 없음 화면으로 분기한다.
- `429`는 rate limit 메시지와 재시도 가능 시각을 표시한다.
- API Key와 전화번호가 포함된 오류 payload는 화면 표시 전에 마스킹한다.

```ts
type ApiError = {
  status: number;
  code: string;
  message: string;
  requestId?: string;
};
```

### 10.2 API Base URL

```env
VITE_APP_URL=https://ars2fa.baro.me
VITE_API_BASE_URL=https://ars2fa.baro.me/api
VITE_ADMIN_BASE_PATH=/admin
```

ARS 인증 API(`/v1/ars/*`)는 모바일 앱/SDK가 호출하는 API이므로 포털 프론트엔드에서는 테스트 호출 화면 또는 문서 예제에서만 사용한다.

## 11. 인증/권한 설계

### 11.1 사용자 인증

```mermaid
sequenceDiagram
    participant Browser
    participant FE as Frontend
    participant API as Backend /api

    Browser->>FE: /login 접속
    FE->>API: POST /auth/login
    API-->>FE: Set-Cookie 또는 token
    FE->>API: GET /me
    API-->>FE: 사용자/권한 정보
    FE-->>Browser: 사용자 대시보드 표시
```

### 11.2 관리자 인증

- `/admin` 진입 시 관리자 세션을 확인한다.
- 프론트엔드 `AdminRouteGuard`는 UX를 위한 1차 가드만 수행한다.
- 관리자 API는 백엔드에서 role을 재검증한다.
- `SUPER_ADMIN`, `REVIEWER`, `OPERATOR`, `KEY_MANAGER` 역할별 메뉴 노출을 분리한다.

## 16. 테스트 전략

| 테스트 | 대상 |
|---|---|
| Unit | 마스킹 유틸, validator, role guard |
| Component | 신청 폼, Key 발급 결과, 인증 로그 테이블 |
| Integration | 로그인, 신청 제출, 관리자 승인, Key 목록 갱신 |

| Accessibility | 주요 폼/테이블 키보드 조작, label, contrast |

## 17. 향후 분리 기준

아래 조건이 발생하면 사용자 포털과 관리자 콘솔을 별도 앱으로 분리할 수 있다.

- 관리자 기능이 많아져 번들 크기와 배포 주기가 사용자 포털과 달라진다.
- 관리자 콘솔을 VPN 또는 내부망 전용으로 완전히 분리해야 한다.
- 사용자 포털은 공개 마케팅/SEO가 중요해 SSR이 필요하다.
- 관리자 콘솔에 별도 디자인 시스템 또는 권한 모델이 필요하다.
