# 07. 인프라 아키텍처

## 1. 목적

이 문서는 `ars2fa` 발신 ARS 인증 API 신청 사이트와 인증 API Gateway를 운영하기 위한 인프라 구성을 정의한다.

구성 방향은 초기에는 Coolify 단일 서버로 단순하게 시작하고, API 사용 앱 수와 인증 로그 증가에 따라 `easymindmap`의 IDC 기반 인프라 문서(`docs/90-architecture/infra-architecture.md`)와 같은 분리형 구조로 확장하는 것이다.

- 초기 단계: Coolify 단일 서버, 자동 SSL, Docker 기반 배포.
- 확장 단계: Coolify App Host 유지, DB/Redis/Worker 분리.
- 본격 운영 단계: IDC 내부망 `192.168.94.0/24`, Cloudflare DNS -> FortiGate -> Nginx Proxy Manager(NPM), App/DB/Redis/Worker VM 분리.
- 원격 운영: FortiGate IPSec VPN, SSH 2222, 내부 관리 도구 IP 제한.

## 2. 도메인 정책

| 구분 | URL | 공개 여부 | 설명 |
|---|---|---|---|
| 사용자 포털 | `https://ars2fa.baro.me` | 공개 | 회원 가입, API 신청, API Key 관리, 인증 현황 조회 |
| 관리자 콘솔 | `https://ars2fa.baro.me/admin` | 제한 권장 | 관리자 로그인, 신청 승인/반려, API Key 운영 |
| 업무 API | `https://ars2fa.baro.me/api/*` | 공개/인증 필수 | 포털/관리자 화면용 API |
| ARS 인증 API | `https://ars2fa.baro.me/v1/ars/*` | 공개/Key 필수 | 모바일 앱 및 `ars_auth` 위젯 호출 |
| 헬스체크 | `https://ars2fa.baro.me/health` | 공개 가능 | NPM/운영 모니터링용 상태 확인 |

관리자 콘솔은 별도 서브도메인 대신 `ars2fa.baro.me/admin` 경로를 사용한다. 따라서 SSL 인증서, 쿠키, CORS, SameSite 정책은 단일 도메인 기준으로 단순화한다.

## 3. 단계별 아키텍처 전략

ars2fa 사이트는 관리자/신청 포털의 동시 접속자가 많지 않을 것으로 예상된다. 따라서 처음부터 IDC VM 분리 구조로 시작하기보다, API 사용 앱 수와 인증 로그 증가량에 따라 아래 3단계로 확장한다.

| 단계 | 기준 | 권장 구성 | 핵심 목적 |
|---|---|---|---|
| 초기 단계 | API 사용 앱 100개 이내 | Coolify 단일 서버 | 빠른 구축, 낮은 운영 부담, 자동 SSL/배포 |
| 확장 단계 | API 사용 앱 500개 이내 | Coolify + DB/Redis/Worker 분리 | 인증 로그 증가 대응, 안정적 백업, 작업 큐 분리 |
| 본격 운영 단계 | API 사용 앱 500개 이상 | IDC/NPM/L4 + App/DB/Redis/Worker VM 분리 | 고가용성, 성능 확장, 운영 통제 강화 |

### 3.1 초기 단계: API 사용 앱 100개 이내

초기 단계는 Coolify 단일 서버 구성을 권장한다. 사용자 포털과 관리자 콘솔의 동시 접속자는 적고, 핵심 부하는 모바일 앱에서 발생하는 `/v1/ars/install`, `/v1/ars/confirm`, `/v1/ars/recheck` 호출과 인증 로그 저장이다.

```text
[인터넷]
   │
   ▼
[Cloudflare DNS]
  ars2fa.baro.me → Coolify 서버 공인 IP
   │
   ▼
[Coolify Host]
  ├── Reverse Proxy + Let's Encrypt SSL
  ├── Frontend/Admin SPA
  │     ├── /        사용자 포털
  │     └── /admin   관리자 콘솔
  ├── Backend API
  │     ├── /api/*      포털/관리자 업무 API
  │     └── /v1/ars/*   ARS 인증 API Gateway
  ├── PostgreSQL
  ├── Redis
  └── Worker(선택)
       ├── 통계 집계
       ├── CSV 생성
       └── 승인/장애 알림
```

권장 서버 사양:

| 항목 | 권장 |
|---|---|
| CPU | 4 vCPU 이상 |
| RAM | 8 GB 이상, 인증 로그 증가가 빠르면 16 GB |
| Disk | SSD 100 GB 이상, 로그 보관 기간이 길면 200 GB 이상 |
| OS | Ubuntu 22.04 LTS 또는 24.04 LTS |
| 배포 | Coolify Git 연동 배포 |
| SSL | Coolify/Traefik 자동 Let's Encrypt |

초기 단계 필수 운영 기준:

- PostgreSQL 정기 백업을 Coolify 외부 위치에도 보관한다.
- API Key와 휴대폰 번호는 애플리케이션 로그/Coolify 로그에 원문이 남지 않게 마스킹한다.
- `/admin`은 URL 노출 여부와 무관하게 백엔드 관리자 권한 검사를 필수로 한다.
- Redis는 외부 공개 없이 내부 Docker network에서만 접근한다.
- API Key별 rate limit을 애플리케이션 레벨에서 적용한다.
- 인증 로그 테이블은 초기부터 `requested_at`, `api_key_id` 기준 인덱스를 적용한다.

초기 단계에서는 별도 NPM 서버, L4 스위치, 다중 VM 구성이 필수는 아니다. Coolify의 reverse proxy와 Docker 네트워크를 사용해 단순하게 시작하고, DB 백업/로그 마스킹/API Key 제한을 우선 확보한다.

### 3.2 확장 단계: API 사용 앱 500개 이내

API 사용 앱이 늘어나면 포털 접속자보다 인증 로그와 API Key 검증 부하가 먼저 증가한다. 이 단계에서는 Coolify 배포 편의성은 유지하되, 데이터 저장소와 비동기 작업을 분리한다.

```text
[인터넷]
   │
   ▼
[ars2fa.baro.me]
   │
   ▼
[Coolify App Host]
  ├── Frontend/Admin SPA
  ├── Backend API x 2 replicas
  └── Worker
        │
        ├──▶ [PostgreSQL 전용 VM 또는 Managed DB]
        ├──▶ [Redis 전용 VM 또는 Managed Redis]
        └──▶ [외부 ARS 서버 / 메일·SMS Provider]
```

권장 구성:

| 구성 요소 | 권장 |
|---|---|
| App Host | 4~8 vCPU, RAM 16 GB |
| Backend | 2개 이상 replica 또는 PM2 cluster |
| PostgreSQL | 별도 VM/Managed DB, SSD 200 GB 이상 |
| Redis | 별도 VM/Managed Redis, AOF 또는 snapshot 정책 |
| Worker | 통계 집계, CSV 생성, 알림 발송을 API 프로세스와 분리 |
| Backup | DB daily backup + 보관/복구 리허설 |
| Monitoring | API 5xx, DB disk, Redis memory, queue 적체 알림 |

확장 단계 전환 기준:

- API 사용 앱이 100개에 근접하거나 초과한다.
- 인증 로그 저장량이 빠르게 증가해 단일 서버 디스크/백업 시간이 부담된다.
- CSV 다운로드, 월별 통계, 관리자 조회가 API 응답 시간에 영향을 준다.
- Redis rate limit/queue 사용량이 증가한다.
- `/v1/ars/*` API의 95 percentile 응답 시간이 운영 기준을 초과한다.

이 단계에서는 Coolify를 계속 사용할 수 있지만, PostgreSQL과 Redis는 애플리케이션 컨테이너와 장애 도메인을 분리하는 것이 좋다.

### 3.3 본격 운영 단계: API 사용 앱 500개 이상

API 사용 앱이 500개를 넘어서면 인증 로그, API Key 검증, 장애 대응, 운영 감사 요구가 커진다. 이 단계에서는 Easymindmap 참조 인프라와 같은 IDC/NPM/VM 분리 구조를 목표 구성으로 사용한다.

```text
[인터넷]
   │
   ▼
[Cloudflare DNS]
  ars2fa.baro.me → 218.232.94.74
   │
   ▼
[FortiGate]
   │
   ▼
[NPM 또는 L4 + NPM]
   │
   ├──▶ App VM #1 Backend/Frontend
   ├──▶ App VM #2 Backend replica
   ├──▶ DB VM PostgreSQL Primary
   ├──▶ DB Replica VM(선택)
   ├──▶ Redis VM
   └──▶ Worker VM Pool
```

본격 운영 단계의 핵심은 아래와 같다.

- App VM을 2대 이상으로 확장하고, NPM 또는 L4 VIP로 분산한다.
- PostgreSQL은 Primary/Replica 또는 최소한 별도 DB VM으로 운영한다.
- 인증 로그 테이블은 월별 파티셔닝과 집계 테이블을 적용한다.
- Worker VM을 분리해 통계, CSV, 알림, 로그 후처리를 큐 기반으로 처리한다.
- 관리자 콘솔, NPM UI, DB Studio, SSH는 VPN/내부망으로 제한한다.
- API Key 단위 rate limit, IP 기준 rate limit, 앱명/플랫폼 검증을 모두 적용한다.

### 3.4 단계별 전환 요약

| 전환 | 유지 | 변경 |
|---|---|---|
| 초기 -> 확장 | Coolify 배포, 단일 도메인, `/admin` path | DB/Redis 분리, Worker 분리, Backend replica |
| 확장 -> 본격 운영 | 도메인 정책, API Key 검증 정책, DB 스키마 | NPM/L4 도입, App VM 다중화, DB replica, 운영망/VPN 강화 |

## 4. 본격 운영 단계 전체 인프라 구성도

아래 구성은 API 사용 앱 500개 이상 또는 인증 로그/운영 통제가 충분히 커진 경우의 목표 아키텍처이다. 초기 단계와 확장 단계에서는 앞의 Coolify 기반 구성을 우선 적용한다.

```text
[인터넷]
   │
   ▼
[Cloudflare DNS]
  ars2fa.baro.me → 218.232.94.74 (A 레코드)
  Proxy: DNS only 권장
  ※ NPM이 Let's Encrypt SSL을 처리
   │
   ▼
[FortiGate 방화벽]
  공인 IP  : 218.232.94.74
  공개 포트: 80, 443
  운영 접속: IPSec VPN, 필요 시 RDP/SSH는 허용 IP 제한
   │
   ▼ NAT → 192.168.94.0/24
   │
   ├────────────────────────────────────────┐
   ▼                                        ▼
[NPM 서버]                            [L4 스위치 - 확장 시]
  내부 IP: 192.168.94.74                 VIP: 192.168.94.2
  역할: Reverse Proxy + SSL              역할: App VM 다중화 시 내부 부하분산
  도메인: ars2fa.baro.me
   │
   ├── /, /admin       → VM-02 Frontend :5173
   ├── /api/*          → VM-02 Backend  :3000
   ├── /v1/ars/*       → VM-02 Backend  :3000
   └── /health         → VM-02 Backend  :3000
```

## 6. 본격 운영 VM 배치 권장안

Easymindmap 인프라와 동일하게 NVMe 용량과 CPU 성능이 높은 ESXi 호스트에 I/O 집약 VM을 배치한다.

| VM | IP | Hostname | ESXi 권장 | 역할 |
|---|---|---|---|---|
| VM-DEV | `192.168.94.120` | `ars-dev` | `192.168.94.11` | 개발 서버, Docker 기반 통합 개발 스택 |
| VM-02 | `192.168.94.122` | `ars-app` | `192.168.94.12` | Frontend/Admin SPA, Backend API Gateway |
| VM-03 | `192.168.94.123` | `ars-db` | `192.168.94.11` | PostgreSQL/Supabase, 인증/신청 데이터 저장 |
| VM-04 | `192.168.94.124` | `ars-redis` | `192.168.94.80` | Redis, Rate Limit, Queue, 세션 캐시 |
| VM-05 | `192.168.94.125` | `ars-worker` | `192.168.94.12` | 통계 집계, 알림 발송, 로그 후처리 |

본격 운영 단계에서는 VM-02/03/04/05를 분리하고, 통계 집계와 알림 작업은 VM-05 Worker에서 처리한다.

## 7. 본격 운영 VM 스펙 계획

### 7.1 기준 구성

| VM | vCPU | RAM | Disk | 설명 |
|---|---:|---:|---:|---|
| VM-DEV | 8 | 16 GB | 200 GB | 개발 전체 스택 |
| VM-02 App | 4 | 8 GB | 80 GB | Node/NestJS 또는 동등 Backend, Frontend preview/static serving |

### 7.2 본격 운영 내 확장 기준

| 증가 요인 | 확장 방향 |
|---|---|
| 인증 API 호출량 증가 | VM-02 Backend PM2 cluster instance 증가, L4 VIP 또는 App VM 추가 |
| 인증 로그 증가 | VM-03 PostgreSQL RAM/NVMe 증설, 월별 파티셔닝, read replica 검토 |
| 통계/CSV 다운로드 증가 | VM-05 Worker 분리 및 큐 처리량 증가 |
| Key 검증/Rate Limit 부하 증가 | VM-04 Redis RAM 증설, Redis persistence/replica 검토 |

## 8. Cloudflare DNS 설정

| Type | Name | Content | Proxy |
|---|---|---|---|
| A | `ars2fa.baro.me` | `218.232.94.74` | DNS only 권장 |

주의사항:

- NPM이 Let's Encrypt 인증서를 직접 발급하므로 Cloudflare Proxy는 기본적으로 끈다.
- Cloudflare Proxy를 켜야 하는 경우 SSL 모드, 원본 인증서, client IP 전달 정책을 별도 검토한다.
- 관리자 콘솔은 `/admin` path 기반이므로 별도 DNS 레코드는 필요 없다.

## 9. Nginx Proxy Manager 라우팅

### 9.1 Proxy Host 기본 설정

| 항목 | 값 |
|---|---|
| Domain Names | `ars2fa.baro.me` |
| Scheme | `http` |
| Forward Hostname | `192.168.94.122` |
| Forward Port | `5173` |
| Websockets Support | 필요 시 활성화 |
| SSL | Let's Encrypt, Force SSL, HTTP/2, HSTS |

### 9.2 Advanced 라우팅 예시

```nginx
# Backend 업무 API
location /api/ {
    proxy_pass         http://192.168.94.122:3000/api/;
    proxy_http_version 1.1;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
    proxy_connect_timeout 10s;
    proxy_read_timeout    60s;
    limit_req zone=api burst=30 nodelay;
}

# ARS 인증 API - 모바일 앱 호출 경로
location /v1/ars/ {
    proxy_pass         http://192.168.94.122:3000/v1/ars/;
    proxy_http_version 1.1;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
    proxy_connect_timeout 10s;
    proxy_read_timeout    60s;
    limit_req zone=auth burst=10 nodelay;
}

# 헬스체크
location /health {
    proxy_pass         http://192.168.94.122:3000/health;
    proxy_set_header   Host $host;
}

# SPA 라우팅: /admin 새로고침도 프론트엔드로 전달
location / {
    proxy_pass         http://192.168.94.122:5173;
    proxy_http_version 1.1;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
}

add_header X-Frame-Options        SAMEORIGIN;
add_header X-Content-Type-Options nosniff;
add_header Referrer-Policy        strict-origin-when-cross-origin;
```

### 9.3 NPM Rate Limit 전역 설정

```nginx
limit_req_zone $binary_remote_addr zone=api:10m  rate=60r/m;
limit_req_zone $binary_remote_addr zone=auth:10m rate=20r/m;
limit_req_zone $binary_remote_addr zone=admin:10m rate=30r/m;
```

애플리케이션 레벨에서도 API Key별 rate limit을 반드시 적용한다. NPM rate limit은 IP 기준 1차 방어로만 사용한다.

## 10. 애플리케이션 배포 구조

VM-02는 Frontend/Admin SPA와 Backend API Gateway를 함께 운영한다.

## 12. 데이터 저장소 설계

### 12.1 PostgreSQL

저장 대상:

- 회원/회사/관리자 계정.
- API 신청 및 심사 이력.
- API Key 해시.
- 인증 요청 최신 상태.
- 인증 이벤트 로그.
- 감사 로그.

운영 권장:

- 인증 로그 테이블은 월별 파티셔닝을 검토한다.
- `auth_requests(api_key_id, requested_at)` 복합 인덱스를 유지한다.
- 전화번호 원문은 저장하지 않고 HMAC 해시와 마스킹값만 저장한다.
- 느린 쿼리 로그를 활성화한다.

### 12.2 Redis

사용 대상:

- API Key 검증 결과 단기 캐시.
- IP/API Key별 rate limit counter.
- 인증 현황 CSV 생성 작업 큐.
- 알림 발송 큐.
- 관리자 세션 또는 refresh token denylist.

## 13. 외부 연동

| 연동 대상 | 방향 | 용도 |
|---|---|---|
| 기존 ARS 서버 `barocall.baro.so` | VM-02 -> 외부 | install/confirm/recheck 중계 |
| 메일/SMS Provider | VM-02/VM-05 -> 외부 | 이메일 인증, 승인/반려, 장애 알림 |
| GitHub | VM-DEV/VM-02 -> 외부 | 배포 소스 pull |
| Cloudflare | 운영자 -> 외부 | DNS 관리 |

기존 ARS 서버 장애는 `ARS_PROVIDER_ERROR`로 표준화하고, 인증 이벤트 로그에 provider 응답 상태와 마스킹된 응답을 저장한다.

## 14. 백업 전략

| 대상 | 방식 | 주기 | 보관 |
|---|---|---|---|
| PostgreSQL | `pg_dump` gzip 백업 | 매일 새벽 | 상세 정책에 따라 30일 이상 |
| 인증 로그 집계 | 일별 통계 테이블 백업 | 매일 | 장기 보관 |
| 환경 변수/설정 | 암호화된 별도 저장소 | 변경 시 | 최신 + 주요 변경 이력 |
| NPM 설정 | NPM data 디렉터리 백업 | 변경 시/주기적 | 복구 가능 기간 |

복구 절차는 운영 리허설을 통해 검증해야 한다. 특히 API Key 원문은 저장하지 않으므로 DB 복구 후에도 기존 Key 원문 재노출은 불가능하다는 점을 운영 정책에 명시한다.

### 15.1 헬스체크

| 체크 | URL/대상 | 기준 |
|---|---|---|

### 15.2 알림 지표

- 인증 API 5xx 비율 증가.
- 기존 ARS 서버 timeout 증가.
- `UNAUTHORIZED_API_KEY`, `APP_NOT_ALLOWED` 급증.
- API Key별 월 한도 80%/100% 도달.
- DB disk 사용량 80% 초과.
- Redis memory 사용량 80% 초과.
- Worker queue 적체.

## 16. 운영 보안

- 모든 공개 트래픽은 HTTPS로 강제한다.
- `/admin` 화면 접근은 관리자 로그인과 서버 권한 검사를 필수로 한다.
- 관리자 세션은 짧은 idle timeout과 재인증 정책을 적용한다.
- NPM Admin UI, DB Studio, SSH는 VPN/내부망에서만 접근한다.
- API Key와 휴대폰 번호는 로그에서 마스킹한다.
- 서버 간 secret은 `.env` 평문 배포 대신 별도 secret 관리 체계로 이전하는 것을 권장한다.
- 운영 배포 전 `ars_auth` 모바일 앱에서 debug log가 API Key를 출력하지 않는지 확인한다.

## 18. 단계별 전환 체크리스트

| 단계 | 완료 기준 | 다음 단계 전환 신호 |
|---|---|---|

| 본격 운영 단계: API 사용 앱 500개 이상 | NPM/L4, App VM 다중화, DB VM/Replica, Redis VM, Worker Pool, VPN 기반 운영망 | 다중 리전, DR, 전용 관제/보안 체계 필요 |
